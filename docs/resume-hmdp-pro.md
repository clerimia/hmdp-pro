## 1. 分布式 ID 生成（UidGenerator）

**简历正文：**

> 改造百度 UidGenerator 作为全局订单号生成器：官方未发布到 Maven 中央仓库，将源码 vendor 进项目并做两处适配（剥离 commons-lang 2.x 依赖、worker 节点分配由 MyBatis 改为 JdbcTemplate）；采用环形缓冲区模式，启动时预生成 `8192 << 3 = 65536` 个 ID 填满 RingBuffer，取号走无锁 CAS，缓冲区余量低于 50% 时异步补货、另有 60s 定时补货兜底，把取号从"每次一次网络/DB"压成 JVM 内存里的指针推进。位分配 `sign(1) + timestamp(28) + workerId(22) + sequence(13) = 63bit`；将官方默认 epoch 从 2016-05-20 前移到 2026-01-01，规避 28bit 秒级时间戳耗尽（官方默认值在 2024 年已耗尽），可用约 8.5 年。订单号在库存预扣**之前**生成，使 Redis 预占事实与订单可逐笔对账；ID 不可枚举这一性质同时支撑了结果查询接口"排队状态命中时不校验归属"的取舍，省掉降级窗口里最贵的那次 DB 查询。

**【追问准备】**

| 追问 | 怎么答（一句话 + 展开） |
|---|---|
| 为什么是 63 位不是 64 位？ | Java 的 `long` 是有符号的，最高位是符号位。百度把它固定为 0，所以 ID 恒为正数，存 MySQL `BIGINT` 不会撞上负数/无符号的坑。剩下 63 位才用于分配。 |
| 时间戳耗尽怎么处理？ | 28bit 秒 ≈ 2.68 亿秒 ≈ 8.5 年。三种解法：调大 `time-bits`（从 seq 或 worker 借位，秒杀场景 worker 用不到 22bit 那么多）、迁移 epoch（改配置重启，新 ID 从新 epoch 起算，历史 ID 不受影响，因为位结构没变只是基准变了）、或者干脆换毫秒级时间戳。本项目选了迁移 epoch 这个成本最低的。 |
| workerId 怎么分配？为什么能不重复？ | 启动时向 `worker_node` 表插一条记录拿自增主键，模 2^22 得 workerId，之后常驻内存不再申请（`DisposableWorkerIdAssigner`）。数据库自增主键保证全局唯一；节点数超过 2^22 才会回绕，实际不可能。 |
| RingBuffer 为什么用数组不用链表？ | 数组连续内存，对 CPU cache line 友好，而且可以用 `sequence & (size-1)` 位运算取模（size 必须是 2 的幂，代码里有 `Assert` 强校验）。 |
| 为什么 tail/cursor 要 `PaddedAtomicLong`？ | 伪共享：两个 `AtomicLong` 挨在一起会落在同一个 64 字节 cache line 里，生产者改 tail 会让消费者读 cursor 的 cache line 失效，来回失效的性能损耗比加锁还狠。填充到独占 cache line 后二者互不干扰。 |
| 为什么 `put` 用 synchronized 而 `take` 无锁？ | 生产是单线程批量补货（一次生成一整秒的 8192 个 ID 再逐个 put），串行即可，加锁没争议；消费是高并发取号路径，必须无锁，用 `cursor.updateAndGet` 自旋推进。读写通过 slot 的 flag 数组（CAN_PUT/CAN_TAKE）做可见性握手。 |
| 取号会阻塞吗？缓冲区空了怎么办？ | 默认 `RejectedTakeBufferHandler` 直接抛异常。实际不会触发：余量低于 50%（32768 个）就异步补货，且补货由 `AtomicBoolean` CAS 保证单线程执行，60s 还有一次定时兜底。 |

## 2. 秒杀主链路：事务消息 + 异步落库 + 三层防重

**简历正文：**

> 用 RocketMQ 事务消息把"Redis 预扣库存"与"订单消息最终可消费"绑成原子：先发半消息，Broker 落盘后才在本地事务里执行 Lua（原子完成扣库存、`sismember` 一人一单、写事务标记与认领映射），成功 COMMIT、库存不足/重复则 ROLLBACK，异常置 UNKNOW 由 Broker 回查标记决定去留。**顺序是关键**——MQ 挂了根本走不到 Lua 那一步，因此不存在"扣了库存却发不出消息"，故障注入实测返回 5004 且 Redis 库存未被误扣。落库侧幂等键取订单主键 `orderId` 而非 `(userId, voucherId)`（一人一单已在入口 Lua 拦掉，消费者根本收不到一人多单的消息），且必须**先 insert 再扣库存**并放在同一事务：消息重投时 insert 撞主键、事务回滚，库存压根不会被扣；反过来先扣库存则会"扣了再补"，白白多两次写和一段中间态。三层防重分别为：入口 Lua 挡热点、主键幂等挡消息重投、`(user_id, voucher_id)` 唯一索引挡最终漏网；消费端业务走独立线程池（有界队列 100 + AbortPolicy），DB 慢时是"快速拒并重投"而不是"慢慢排队"。

**【追问准备】**

| 追问 | 怎么答 |
|---|---|
| 为什么不用「先扣库存再发普通消息 + 本地消息表」？ | 也能做，但要自建 Outbox 表和投递线程。事务消息把这些交给 Broker：半消息对消费者不可见，回查机制天然解决"本地事务成功但 COMMIT 没发出去"的窗口。代价是每单多一次半消息落盘和一次回查的可能性，换来的是不用自己维护 Outbox。 |
| 事务回查查的是什么？ | `seckill:txn:{orderId}` 这个标记，它和扣库存写在同一个 Lua 脚本里，所以"标记存在" ⟺ "库存已扣"。标记 TTL 1 小时，覆盖 Broker 回查窗口。 |
| 回查为什么用 redisBreaker 而不是 dbBreaker？ | 按依赖拆分爆炸半径：回查查的是 Redis 标记，就该计入 Redis 熔断器。用 dbBreaker 的话，Redis 一挂会把"DB 熔断器"打开，传导到入口让新订单误报"处理中"——依赖归因错了会让降级动作指向错误的组件。 |
| 消费端为什么去掉了 Redisson 锁 + count 预查？ | 它们保护的是"一人一单"，而入口 Lua 已经保证了，消费端再串行化纯属重复：每单多 2 次 Redis 往返 + 1 次 SELECT，同一用户的订单全部排队，`tryLock(2s)` 在挤压时会迅速占满业务线程池。 |
| 消费线程池为什么独立？ | RocketMQ 拉取线程被拖死会导致消息拉取停摆（不只是这一批慢）。独立池 + 有界队列让故障期表现为"队列满 → 整批延迟重投"的自然背压，拉取线程始终健康。 |

## 3. 多级缓存与一致性

**简历正文：**

> 读链路为 Caffeine(L1, JVM) → Redis(L2, 逻辑过期) → MySQL(L3)：L1 上限 1 万条、写后 30s 过期（短 TTL 是有意的——本地缓存无法跨实例主动失效，驱逐通知只会命中发起写操作的那个实例，跨实例脏数据只能靠 TTL 自愈，30s 把一致性窗口从 10min 压到 30s）；L2 用逻辑过期，命中过期值时先返回旧数据再由异步线程持 Redisson 锁重建，请求不阻塞；穿透用空值标记 + 随机 TTL，雪崩用 TTL ±20% 抖动，击穿用互斥锁 + 双重检查 + **有界等待 1s**（超限自行回源 DB，杜绝无界递归把请求线程占死）。一致性上处理了一个隐蔽竞态：**回源查 DB 与写回缓存之间的空隙里若有更新提交并删缓存，旧快照会被写回，且带着崭新的逻辑过期时间和重置的物理 TTL，等于给脏数据续命、系统外观一切健康**——解法是写回前比对快照 `update_time` 与 DB 当前行版本（由 `ON UPDATE CURRENT_TIMESTAMP` 维护，天然是行级版本号），落后则放弃写回；版本权威必须取自 DB 而非 Redis 现值，因为删除式 Cache-Aside 下竞态最致命的形态恰好发生在 key 被删之后，此时 Redis 里没有值可比。更新走**事务提交后**（`TransactionSynchronization#afterCommit`）失效两级缓存，失败短退避重试 2 次、仍失败只告警不阻断；同时挂 3 倍逻辑 TTL 的物理 TTL 保险丝，把"永久脏"变成最迟 90 分钟自愈的有限窗口。

**【追问准备】**

| 追问 | 怎么答 |
|---|---|
| 为什么逻辑过期而不是物理过期？ | 物理过期一到点 key 就没了，热点 key 失效瞬间所有请求同时穿透到 DB（击穿）。逻辑过期把过期判断挪进应用层，key 永远有值，命中过期值时返回旧数据 + 异步重建，DB 只被一个重建线程访问。 |
| 物理 TTL 保险丝为什么还需要？ | 逻辑过期意味着 Redis 侧这个 key 永久不过期。一旦主动删除和异步重建同时失败（Redis 抖动、重建抛异常），脏数据就无限期驻留了。3 倍 TTL 把 ∞ 变成一个有限值，是最后一道兜底。 |
| 为什么没接 Canal 做失效？ | 商铺是低频写、允许有界脏读的场景，物理 TTL 已经把最坏窗口封死在 90min。接 Canal 要多部署一套中间件 + 处理 binlog 解析延迟和乱序，收益是"90min → 约 1s"，不成比例。真要接，先接的是订单/库存这类强一致场景。 |
| L1 30s TTL 会不会让命中率太低？ | 会。这是明确取舍：本地缓存跨实例无法主动失效，TTL 越长一致性越差。30s 是"多实例脏读窗口"和"Redis 读 QPS"之间的平衡点。要两全就得引入广播失效（Redis Pub/Sub 或 MQ 广播），那是另一个量级的复杂度。 |
| 异步重建为什么必须在工作线程内部加锁？ | Redisson 的锁绑定线程，调用方加锁、线程池里解锁会抛 `IllegalMonitorStateException`。而且 `finally` 里不能无条件 unlock——递归/重试路径 return 时会误删他人持有的锁，必须先判 `isHeldByCurrentThread()`。所有 `tryLock` 都显式给 wait/lease，禁用 watchdog，让重建线程挂死时锁最迟 30s 自动释放。 |
| 缓存为什么不放在网关（OpenResty）？ | 两个理由：① 网关的 `lua_shared_dict` 收不到应用层的驱逐通知，只能等 TTL 自然过期，等于在系统里放了第二份无法主动失效的真相；② 它挡在 Java 之前，命中时请求根本不进应用——没有日志、没有 traceId、也没进指标，是彻底的观测黑洞。所以网关职责收敛为限流。 |

## 4. 容错体系（Resilience4j）

**简历正文：**

> 先收敛超时基线：Redis 命令超时从 Lettuce 默认的 60s 压到 **800ms**（默认 60s 时 Redis 挂掉会让每个请求卡 60s，几分钟内占光 Tomcat 线程并雪崩殃及 MySQL），Redisson 800ms/连接 1s/重试 2 次，Hikari 连接 3s + 池 20，所有 `tryLock` 显式 wait/lease 禁用 watchdog。熔断器**按依赖拆分**而非全局共用（Redis 抖动不应熔断 MQ 通道，否则爆炸半径反而变大）：`redisBreaker` 管缓存与事务回查、`mqBreaker` 管发送通道、`dbBreaker` 管消费端落库，均为失败率 50%/滑动窗口 20 次/最少 10 次调用/半开放行 3 次探测；`ignore-exceptions` 含业务异常与 `BulkheadFullException`——库存不足/重复下单是秒杀最高频结果，算进失败率会把健康依赖误熔断，舱壁拒绝是隔离动作也不等于依赖故障。降级语义按路径分野：**读路径降级 = 回源 DB，但必须过 `dbFallbackBulkhead`（许可数对齐 Hikari 池 20），否则 Redis 一挂所有读涌向 DB，降级本身就成了雪崩放大器**；**写路径（秒杀）fail-closed**，无论舱壁满、熔断打开还是 Redis 不可用一律拒绝，因为不超卖的证明唯一依赖 Redis Lua 的原子扣减，Redis 挂了还放行等于拆掉正确性屏障。落库降级时入口诚实返回"处理中"（业务码 1100）并带出 orderId，而不是谎报成功——**说谎的降级比明确的报错更糟**。限流器自身则 fail-open（异常放行并计 `hmdp_ratelimit_fallback_total`），因为它只是保护手段。故障注入实测 🔢：停 MySQL 后 18 笔订单在恢复后 90 秒内全部自动追平、无消息进死信；停 Redis 期间 fail-closed 无超卖；消息重投撞主键回滚、库存零副作用；30 并发抢 10 份库存，375ms 内 10 成功 / 20 库存不足 / 0 重复，Redis 与 DB 双向一致。

**【追问准备】**

| 追问 | 怎么答 |
|---|---|
| 为什么 Redis 超时是 800ms 而不是 200ms 或 3s？ | 要同时满足两个约束：大于 Redis 正常 P99（否则误判故障），小于"Tomcat 线程池被占光"的临界时间。Tomcat 200 线程、假设单请求 50ms，理论吞吐 4000 QPS；Redis 挂时若每请求卡 60s，几秒内线程就全被占满。800ms 下单请求最多浪费 800ms，失败快速上抛给熔断/降级处理，信号量舱壁也就有了意义（舱壁只能拒绝新请求，救不了已卡住的线程）。 |
| `minimum-number-of-calls: 10` 解决什么问题？ | COUNT_BASED 窗口的经典坑：冷启动时样本太少，前两次失败就是 100% 失败率，直接误熔断。设 10 次意味着前 10 次调用只统计不计失败率。代价是故障最初几秒仍会放行（实测前 15 单返回成功），这是明确接受的权衡——成功语义本来就是"Redis 预扣成功"，后面还有重试 + 对账两层兜底。 |
| 为什么 `@Retry` 和 `fallbackMethod` 不能放同一个方法？ | fallback 会把异常"消化"成正常返回，Retry 一次都触发不了。分层后顺序是 熔断(外) → 重试(内)，两次重试都失败才交给外层熔断 + 降级。而且 Retry 只配在只读幂等路径，写路径一律不加——下单重试可能重复扣库存。 |
| fallback 方法上的注解为什么失效？ | `fallbackMethod` 是 R4J 切面反射直调的，不经过 Spring 代理，AOP 注解全部失效。所以 `dbFallbackBulkhead` 只能在代码里用 `BulkheadRegistry` 手动 `tryAcquirePermission` / `releasePermission`。事务消息回查回调同理（跑在 RocketMQ 内部线程上）。 |
| 为什么 Lua 失败必须 `throw` 而不是 `return Result.fail`？ | 熔断器只认"传播到方法外的异常"。事务监听器捕获 Lua 异常后会置 UNKNOW 并把结果标成 -1，秒杀方法如果 `return Result.fail`，对熔断器来说这是一次**成功调用**，它永远学不会熔断。`throw SystemException` 才能被计入失败率并转成 503 语义化快速失败。 |
| MQ 故障的异常为什么在 seckillVoucher 里被转成业务响应而不是上抛？ | 因为 `seckillVoucher` 外层套的是 `redisBreaker`。MQ 故障的异常穿过去会被记成 Redis 失败，把爆炸半径扩散到健康依赖。转成 200 + code=5004 后，redisBreaker 一个失败都不多记。 |

## 5. 可观测性：traceId 链路追踪 + Prometheus 埋点

**简历正文：**

> 自研 traceId 全链路串联（32 位无横线 UUID），所有边界统一走 `TraceContext` 门面读写 MDC，四类边界各接管一次：**HTTP 入口**（Filter，order 最高，上游有 `X-Trace-Id` 就复用）、**线程池**（任务提交时刻快照 MDC，`traceAwareExecutor` 包装，重建/消费线程不再与请求链路断开）、**MQ 发送**（注入消息 properties，不污染业务 body）、**MQ 消费与事务回查**（extract 还原，重试消息带 `-r{n}` 后缀）；traceId 来自外部请求头会先做白名单清洗（防日志注入与超长值），且 `finally` 必须 clear（线程池化复用，不清理会让下一个请求打出上一个请求的 traceId）。指标侧用 Micrometer + Prometheus **pull 模型**（代码里没有"上报"动作，只有内存计数 + 暴露端点，埋点故障不会拖垮业务线程），埋点走 `SeckillMetrics` / `CacheMetrics` / `ResilienceMetrics` 三个语义化门面，业务不直接碰 MeterRegistry；成败共用一个指标名、用 `reason` tag 区分，取值封闭在枚举里，**绝不用 orderId / userId / traceId 当 tag**（每个唯一 tag 组合都是一条独立时间序列，高基数会打爆采集端内存和查询）；埋在决策点而非 IO 前后，手法是"reason 变量贯穿所有分支 + `finally` 统一落定"，保证任何 return 路径都不漏统计。韧性侧订阅 Resilience4j 事件流（error / not_permitted / 状态翻转 / 重试），让"系统当时是否在降级"在 Grafana 上可见——否则用户投诉时无从判断；死信队列配 Grafana Unified Alerting，`increase(hmdp_order_dead_letter_total[5m]) > 0` 即触发邮件告警（`or vector(0)` 是必须的：Counter 首次打点前指标不存在，不补 0 规则永远停在 NoData）。共 13 个看板面板。

**【追问准备】**

| 追问 | 怎么答 |
|---|---|
| 为什么不用 SkyWalking / OpenTelemetry？ | 会换。`TraceContext` 就是为这个留的改动点——换 OTel 只改这一个类的内部实现，四个边界的调用方一行都不用动。现在自研的代价是没有 span 树和耗时瀑布图，只有 traceId 串联，明细靠结构化日志 + traceId 检索。 |
| Metrics / Logs / Trace 三者怎么分工？ | 排查顺序就是这张表：Metrics 回答"异常了吗"（聚合趋势 + 告警），Logs 回答"这一笔为什么失败"（明细下钻，每行带 traceId），Trace 回答"一次请求经过了哪些环节"。 |
| 为什么新建线程池必须用容器里的 `traceAwareExecutor`？ | 自建 `Executors.newFixedThreadPool()` 的话，异步任务的日志与发起请求的那条链路是断的——排查时按 traceId 捞不到缓存重建/异步落库那半段。 |
| 为什么不用 Timer 名手写 `_seconds`？ | Micrometer 会按 Prometheus 约定自动转换：Counter `hmdp.seckill.result` → `hmdp_seckill_result_total`，Timer `hmdp.seckill.latency` → `hmdp_seckill_latency_seconds_*`。自己加后缀会变成 `..._seconds_seconds`。 |
| 指标是 push 还是 pull？有什么影响？ | Pull。Prometheus server 定时来 `/actuator/prometheus` 拉快照，应用侧只做内存自增。所以埋点组件故障不影响业务线程，秒杀这种高频路径逐条 push 的话，一次网络 IO 就会让埋点本身变成瓶颈和故障点。 |

## 6. 分层限流 + 异步兜底（对账 / 死信 / 关单）

**简历正文：**

> 削峰分三层，均为快速拒绝而非排队等待：**① 网关层** OpenResty 共享内存令牌桶（rate 1000/s、capacity 3000）限制集群总入口 QPS；**② 应用层** Redis ZSET 滑动窗口按 `userId` 限流，下单 5 次/秒、查落库 10 次/秒、查支付 10 次/秒**各算各的配额**（共用一个 key 的话前端多查几次结果就把自己的下单额度烧光了，真正想下单时反而吃 429）；**③ 入口层** 信号量舱壁 100（Tomcat 200 线程的一半）`maxWait=0`，许可耗尽立即拒。这里的关键认知是：**限流真正防的是伪造 orderId 反复查询打穿缓存直落 DB，不是防轮询洪峰**——轮询规模被库存数封顶，只有抢到的人才有 orderId 可查，不存在几十万人同时轮询。兜底是四层阶梯：消费失败 → RECONSUME_LATER 延迟重投 → **重试上限从默认 16 次压到 5 次**（默认按 10s→2h 递增、总拖尾近 2 小时，长故障本就该交给对账而不是让重试队列无限拖尾）→ 超限转死信 topic 并告警 → **每分钟一轮的对账任务**兜底。对账以订单表为唯一账本，按 ①关单 → ②补单 → ③库存重算 顺序执行，账本修复必须先于库存重算；三个巧思：**补单复用用户入口拿到的原 orderId**（换新号会让用户轮询旧单号永远 NOT_FOUND，表现为"抢到了但订单消失"）；**本轮发生过补单就跳过库存重算**（补单是异步消息，同轮重算会读到"补的单还没落库"的账本把库存算大，实测修复前凭空多出 1 份库存、持续整整一个调度周期）；**基数相等即无丢单**（订单用户 ⊆ 已扣库存用户集合，故 `COUNT(订单) == SCARD(集合)` 即可判定收敛，热门券每轮只花一次 O(1) + 一次索引 COUNT，不做 `SMEMBERS`）。索引审计实测 🔢：20 万行数据下 3 个对账查询从全表扫描 199515 行降至 1 / 4 / 3 行。

**【追问准备】**

| 追问 | 怎么答 |
|---|---|
| 为什么重试上限要改小？ | 默认 16 次按 10s→2h 递增，总拖尾近 2 小时。故障持续超过几分钟就该交给对账补单兜底，而不是让消息在重试队列里无限拖尾——拖尾期间用户既拿不到结果，占用又是白占。改成 5 次（约 6 分钟）后，超限时 Broker 自动转死信，由告警 + 对账接手。 |
| 对账三个步骤的顺序为什么不能乱？ | 账本修复（关单、补单）必须先于库存重算，因为库存是派生值：`expected = initial_stock − 有效订单数`。先重算的话读到的是还没修好的账本，算出来的数是错的，而且会写进 Redis 立刻生效。 |
| 在途单守卫是什么？ | 活动刚结束的 15 分钟内关单还在发生，此时算出的 expected 下一轮就会被关单改写。所以有 `status=1` 未支付单时直接跳过重算，等全部订单终态后一次算准。 |
| 对账为什么只用 7 天窗口？ | 无下界会每轮全量扫历史券，成本随运营时间无限增长。7 天窗口外的活动不再兜底，key 续期 14 天后自然过期，历史 key 总量有界。 |
| 关单回补库存为什么拆两个幂等标记而不是一个？ | 一个标记挡不住"Redis 半边成功、DB 半边失败"的重投——删标记重做会把 Redis 半边也重做，库存 +2 → 额外用户过闸 → **超卖**。拆成两个标记后，任何路径都不会重做已成功的半边。Redis 侧用 Lua 把 SETNX 与条件 incr 做成原子，天然 exactly-once；DB 侧只在 UPDATE 异常时删标记重投。第一不变量是"永不过补优先于尽量不丢补"：丢补是少卖（方向安全，对账收敛），过补直接击穿入口闸门。 |
| 索引那个 `type=index` 的坑是什么？ | EXPLAIN 显示用了 `uk_user_voucher`，但它是**全索引扫描**不是查找——uk 最左列是 `user_id`，按 `voucher_id` 查时前缀不匹配，等于把整个索引扫了一遍。加 `idx_voucher_status(voucher_id, status)` 后变 `ref`，扫描 199515 行降到 4 行。 |
| 超时关单为什么既有延迟消息又有定时扫描？ | 延迟消息负责及时（15 分钟档位），定时扫描负责兜底（覆盖发送失败、broker 丢失、消费失败进 DLQ 的一切场景），二者通过状态 CAS 幂等共存，并发安全。 |

## 7. 可选：一句话总括（自我介绍 / 项目 overview 用）

> 这个项目的主线是**"让每一条失败路径都有归宿"**——主路径上用 Lua 原子扣减 + 事务消息 + 主键幂等保证不超卖、不重复；主路径之外用熔断降级、有限重试、死信告警、分钟级对账四层兜底保证最终一致；全程用 traceId 和结构化指标让"系统在降级"这件事可见，而不是等用户投诉。

## 9. 讲的时候别踩的坑（自己人提醒）

1. **别把"标准做法"说成"我发明的"**——Lua 扣库存、逻辑过期、Cache-Aside 都是业界通用。你的增量在于**取舍与边界**：为什么 30s、为什么 800ms、为什么比对 DB 而不是 Redis、为什么补单后跳过重算。这些才是能聊十分钟的东西。
2. **主动说"我没做/我选择不做"**——没接 Canal、没有 span 树、没有支付链路、L1 跨实例不主动失效。能说清"为什么不做"比堆十个技术名词更有说服力，面试官也更容易顺着追问到你熟悉的战场。
3. **数字不确定就说"实测约"或干脆不给**——上面第 8 节标了哪些是真的。
4. **fail-open / fail-closed 是贯穿全项目的哲学**，被问到任何"组件挂了怎么办"都可以先抛这条：限流是保护手段 → fail-open；库存/一人一单是正确性屏障 → fail-closed。
