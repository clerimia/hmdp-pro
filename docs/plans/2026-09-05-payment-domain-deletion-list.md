## 1. 三条判据：删的是「场景」，不是「手法」

文档处置最容易犯的错是**按关键词删段落**——看到"支付""关单"就整段删，结果把手法和论证一起扔了。

### 判据一：一段文档讲「用 X 手法解决 Y 场景」，Y 被砍了怎么办？

| 情况 | 处置 |
| --- | --- |
| **手法 X 在改造后仍有别的载体** | **改写**：换掉 Y，保留 X |
| **手法 X 随 Y 一起消失** | **整段删** |

**实例 A（改写）**：README §6「CAS 支付」讲"条件更新保证一单一终态"。场景（支付）没了，但 **CAS 手法的载体换成了核销**：`UPDATE ... SET used=1, use_time=NOW() WHERE id=? AND used=0`，影响行数 0 即已核销、直接跳过。**删掉这一节就等于丢掉 CAS 叙事**，必须改写而不是删。

**实例 B（删除）**：`resume-hmdp-pro.md` 的问答「关单回补库存为什么拆两个幂等标记？」。手法（双半边幂等回补）随关单一起消失，改造后没有任何地方需要"回补库存"（撤回走 DELETE + 对账自愈）。**整条删**——但它承载的原则「永不过补优先于尽量不丢补」值得压缩成一句话挪到对账那条问答里（对账的误差方向是单侧的：宁可少卖不可超卖）。

### 判据二：结论按**类型**分，不按它出现的位置分

| 类型 | 定义 | 处置 |
| --- | --- | --- |
| **机制类** | "X 机制能/不能收敛 Y 类问题" | Y 改造后仍存在 → **改写保留**（换 X 的名字，保留结论）；Y 随 X 消失 → **删** |
| **参数类** | 带具体数字的性能/规模结论（扫描行数、耗时、档位、阈值） | 其依赖的 SQL 谓词或配置变了 → **数字作废，需重测**。**禁止拿旧数字充当新论证**；留作"改造前基线"必须显式标注 |
| **事实类** | "现场发生过什么"（某次故障的现象与恢复过程） | **一律保留**，标注时间戳与"改造前"——不可复现，删了永久丢失 |

### 判据三：`pay` 前缀 ≠ 支付域

**支付域 = "钱从用户流向系统"这条链路。**
`tb_voucher.pay_value`（券的面值/抵扣金额）描述的是**这张券值多少钱**，是券的属性，与"用户付钱给系统"无关。

> 按 `pay` 关键字无脑 grep 删除，会先删掉券的价格。**这是本清单里最贵的陷阱。**

### 2.7 README / 简历共用的新增一节：「券的生命周期：领取 → 核销」

被删的 README §5、§6 与简历里"15 分钟延迟关单"那段，共同丢掉的技术点是 **CAS 条件更新**。用下面这节补回来（三处文档共用同一份内容，措辞按场合调整）：

> **问题**：券领到手之后还有第二次状态迁移——到店核销。核销动作可能重复提交（商家端连点、网络重试），"先查状态再更新"会把 `use_time` 覆盖掉。
> **做法**：核销走一条 CAS：`UPDATE tb_voucher_order SET used = 1, use_time = NOW() WHERE id = ? AND used = 0`。影响行数 1 = 首次核销成功，0 = 已核销过（直接跳过，不覆盖时间）。**把状态判断压进 WHERE，就不存在 check-then-act 的竞态窗口**，不需要幂等标记、不需要分布式锁、不需要先查后写。
> **连带约束**：`used` 与 `use_time` 的合法组合由 MySQL 8 的 CHECK 约束 `chk_used_consistency` 锁死（`(used=0 AND use_time IS NULL) OR (used=1 AND use_time IS NOT NULL)`），脏数据根本存不进去。
> **范围**：核销由商家端/线下触发，**本项目不提供核销接口**（只保证数据模型能表达它、种子数据有样本、对账口径不因它出错）。

## 6. `used` 的命名核实与 Java 类型（票第 5 问）

### 6.1 MySQL 保留字核实：**不是保留字，而且根本不是关键字**

对着 MySQL 8.0 官方关键字表（`https://dev.mysql.com/doc/refman/8.0/en/keywords.html`，2026-09-05 抓取核对）：

| 词 | 是否在关键字表里 | 是否保留 |
| --- | --- | --- |
| **`USED`** | **否 —— 整张表里不存在这个词** | 否 |
| `USE` | 是 | **保留** |
| `USAGE` / `USER` / `USING` / `USER_RESOURCES` / `USE_FRM` | 是 | 保留 |
| `STATUS` | 是 | **非保留** |

**`US*` 家族在 8.0 表里恰好 6 个**：USAGE · USE · USER · USER_RESOURCES · USE_FRM · USING。`USED` 不在其中。

**结论：`used` 作列名可以裸写，不需要反引号。** 本项目 DDL 习惯给所有列加反引号，照旧加即可（无害）。

**顺带修正票里的一个说法**：票写"MySQL 8 保留字表里有 `USE`/`USAGE`/`USING`"——这个是对的。但**现在正在用的 `status` 其实是非保留关键字**，它本来就能裸写，只是 DDL 习惯加了反引号。这条对我们无影响（`status` 要删），但说明"要不要加反引号"在本项目里从来不是问题。

### 6.2 Java 侧定 `Integer used`，不用 `Boolean isUsed`

| 方案 | Lombok 生成的方法 | JavaBeans 属性名 | 能否直接对上列 `used` | 结论 |
| --- | --- | --- | --- | --- |
| **`Integer used`** | `getUsed()` / `setUsed()` | `used` | ✅ 天然对齐，**零配置** | **选它** |
| `boolean used` | `isUsed()` / `setUsed()` | `used` | ✅ 对齐 | 可用，但见理由 4 |
| `Boolean isUsed` | **`getIsUsed()` / `setIsUsed()`** | **`isUsed`** | ❌ 会去找列 `is_used`，**必须补 `@TableField("used")`** | **否决** |

**Lombok 的坑（必须写清）**：`is-` 前缀的省略规则**只对基本类型 `boolean` 生效**——`boolean isUsed` 生成 `isUsed()` / `setUsed()`。字段类型是**包装类 `Boolean`** 时，Lombok 按字段名老实生成 `getIsUsed()` / `setIsUsed()`，JavaBeans 内省出的属性名变成 **`isUsed`**，与列名 `used` 对不上。

> **项目里已有的 `Blog.isLike`（`Blog.java:57`）不构成反例**——它带 `@TableField(exist = false)`，是非持久化字段，根本不参与列名映射。这个反例很容易被拿来"证明 `Boolean isXxx` 能用"，实际上证明不了。

**选 `Integer used` 的四条理由：**

1. **与刚删掉的 `status` 完全同构**（`tinyint(1) unsigned` → `Integer`）。改造前后 Java 侧写法不变，diff 最小；而且这条映射路径**已被混沌测试实测跑通**（`status` 的读写一直在用）。
2. **零配置**，不需要 `@TableField`。**多一个注解就是多一处将来被漏改的地方**——这类注解在改名时最容易被忘掉，而忘掉的表现是运行时才炸。
3. **列是 `NOT NULL DEFAULT 0`**，用可空的 `Boolean` 反而引入一个 DB 层不允许的第三态。
4. **返回值口径**：上游 §5.4 定 `getSeckillResult` 返回 `data.put("used", order.getUsed())` → `0` / `1`。`Integer` 直接满足；`Boolean` 会返回 `true`/`false`，与 §5.4 的文字冲突。

**`used` 在 Java 侧也不是关键字**，两边都能裸写。
