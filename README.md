# HMDP-Pro

校园餐饮评价与优惠平台——基于 Spring Boot / MySQL / Redis / RocketMQ 的高并发领券系统，配套 pytest + Playwright + JMeter 三层自动化测试体系，覆盖登录、两级缓存、高并发领券三条核心链路。  
仓库：[https://github.com/clerimia/hmdp-pro](https://github.com/clerimia/hmdp-pro)

黑马点评已经把 Redis 缓存、Lua 秒杀、一人一单、异步下单等主干讲清楚了，足够入门。落到更高并发与更长链路时，仍容易碰到：入口缺少分层限流、扣库存与发消息之间一致性偏弱、券的生命周期不完整（只有发放没有核销）、缓存更新缺少主动失效、主路径之外几乎没有对账兜底。本仓库以校园餐饮优惠场景为载体，在保留原有技术模型的前提下按更接近生产的方式补强这些能力，方便对照学习与面试表述。

------

### 1. 入口分层限流与预热校验

**问题：** 领券入口用 Lua 同步扣 Redis 库存并做一人一单；网关只能限制进入应用的 QPS，放行后的峰值仍打在入口 Redis 热点上。此外库存与活动时间只在发布秒杀券时写入 Redis，直接改库会让领券恒返回「库存不足」却没有任何报错；活动没开抢或已结束也照样能领。  
**做法：** 削峰分三层——OpenResty 网关令牌桶（分布式）、应用层按 userId 的滑动窗口、入口信号量舱壁（100，许可耗尽立即拒）。入口先经预热服务拿到活动窗口，拦掉未开始与已结束的请求再走 Lua。**库存回填只在活动开始前安全**：活动开始后 Redis 库存才是真值，DB 的 stock 落后于它（订单异步落库），拿 DB 回填会把已扣掉的库存加回去而直接超卖——所以宁可让领券失败，也不回填。

### 2. 事务消息

**问题：** 原版常见「先 Lua 扣 Redis，再发异步消息」，发送超时或进程中断时会出现库存已扣无单、或回滚与重复投递纠缠。  
**做法：** 默认写路径改用 RocketMQ **事务消息**：先发半消息，在本地事务中执行领券 Lua（扣库存、一人一单、写事务标记），成功则 COMMIT、失败则 ROLLBACK。Broker 可通过回查事务标记决定半消息去留，把「扣减成功」和「创建单消息最终可消费」绑在一起。

### 3. 一人一单

**问题：** 只靠查订单表或 Redis Set，在连点、多实例和消息重试下仍可能插入多单。  
**做法：** 入口用 Redis Lua **原子**判断是否已领取（扣库存 + `sismember` + 写事务标记在同一脚本内）；消费者落库时**先 insert**，靠**订单主键 orderId** 幂等去重（消息重投会撞主键，事务回滚后库存压根没扣）；数据库对 `(user_id, voucher_id)` 建 **唯一索引** 兜住漏网。三层分别挡热点、挡消息重投、挡最终漏网。

### 4. 对账

**问题：** 主路径之外缺少对消息丢失、库存漂移、资格与订单不一致等残留的修复。  
**做法：** 用 Spring 定时任务跑对账：以订单表为账本，补齐丢失的领取记录，并按已领取数重算校正 Redis 与 MySQL 库存。事务消息负责主路径尽量不错，对账负责错了之后收敛。

### 5. 券的生命周期：领取 → 核销

**问题：** 券领到手之后还有第二次状态迁移——到店核销。核销动作可能重复提交（商家端连点、网络重试），「先查状态再更新」会把 `use_time` 覆盖掉。  
**做法：** 核销走一条 CAS 条件更新：`UPDATE tb_voucher_order SET used = 1, use_time = NOW() WHERE id = ? AND used = 0`。影响行数 1 = 首次核销成功，0 = 已核销过（直接跳过，不覆盖时间）。**把状态判断压进 WHERE，就不存在 check-then-act 的竞态窗口**，不需要幂等标记、不需要分布式锁、不需要先查后写。  
**连带约束：** `used` 与 `use_time` 的合法组合由 MySQL 8 的 CHECK 约束 `chk_used_consistency` 锁死（`(used=0 AND use_time IS NULL) OR (used=1 AND use_time IS NOT NULL)`），脏数据根本存不进去。  
**范围：** 核销由商家端/线下触发，**本项目不提供核销接口**（只保证数据模型能表达它、种子数据有样本、对账口径不因它出错）。明确不接三方支付：券免费领，用户到店线下付钱给商家——「已使用」≠「已支付」。

### 6. 二级限流（令牌桶 + 滑动窗口）

**问题：** 缺少分层限流时，洪峰请求占满 Tomcat/Redis，成功请求也被拖垮并引发重试放大。  
**做法：** 第一层在 **OpenResty/网关** 用共享内存 **令牌桶** 限制集群总入口 QPS，超额直接返回繁忙。第二层在应用内用 Redis **滑动窗口** 按 `userId` 限制领券调用频率。两层都是快速拒绝，不在入口线程里阻塞等待。

### 7. 多级缓存

**问题：** 商铺详情多为 Redis → MySQL，热点仍反复打 Redis；更新后若只靠 TTL，脏读窗口偏长。  
**做法：** 读路径为 **Caffeine 本地缓存 → Redis（逻辑过期）→ MySQL**；逻辑过期命中旧值时先返回旧值，再由异步线程持 Redisson 锁重建，避免击穿。更新时在**事务提交后**同步删除 Caffeine 与 Redis（失败短退避重试 2 次，仍失败只告警不阻断业务）。一致性兜底：逻辑过期缓存额外挂 3 倍逻辑 TTL 的**物理 TTL 保险丝**，evict 失败或重建持续失败时脏数据最迟 90min 自愈，不存在「永久脏」路径。**明确不接 Canal**：商铺低频写、允许有界脏读，物理 TTL 已封死最坏窗口，接入 Canal 需要额外部署与运维，收益（脏窗口 90min → ~1s）不成比例；L1 本地缓存无法跨实例主动失效，靠 30s 短 TTL 自愈。

**为什么缓存不放在网关（OpenResty）：** 网关的 `lua_shared_dict` 收不到应用层的缓存驱逐通知，只能等 TTL 自然过期——等于在系统里放了第二份无法主动失效的真相；更糟的是它挡在 Java 之前，一旦脏了，前端怎么刷新都是旧值。因此网关职责收敛为**限流**（`src/main/resources/openresty/` 只保留令牌桶），缓存全部收回应用层，失效路径才闭环。

### 8. 读写链路分离

**问题：** 查询与领券写共用同步资源时，写路径拖慢读、读洪峰又挤占领券线程与连接。  
**做法：** 读请求走多级缓存链路，不进入领券 Lua/事务消息路径；写请求走限流 + 写策略 A/B + MQ 异步落库 + 对账。这里的分离是业务链路隔离，不是 MySQL 主从复制。

## 术语表

| 词 | 用在哪 | 含义 | 不要用在哪 |
| --- | --- | --- | --- |
| **领券** | 接口 / 文档 / 测试用例命名、对外叙事 | 用户免费领取一张优惠券的动作 | — |
| **抢券** | 简历与面试口述（必要时补一句"就是领券，限时限量所以叫抢"） | 同上，但带出并发与正确性叙事 | 不要写进接口名 / 测试用例名 / UI 文案 |
| **已领取** | 人读处描述 `used = 0` | 券在用户手里、还没到店核销 | 不要写成"未支付""待支付" |
| **已使用 / 已核销** | 人读处描述 `used = 1` | 券已到店核销 | 不要写成"已支付" |
| **`used`** | 代码与 DDL | `0` = 已领取未使用；`1` = 已使用 | 人读处不要直接写 `used=1`，写"已使用" |
| **`seckill`** | 代码标识符、Redis key 前缀（`seckill:stock:` 等）、指标名（`hmdp.seckill.*`）、类名方法名 | 这条领券链路的**技术实现**：限时限量 + Lua 原子预扣 + 事务消息 + 异步落库 | 不要出现在面向用户的文案与文档标题里 |
| **订单 / `tb_voucher_order` / `VoucherOrder`** | 数据模型层 | 表名与类名沿用，但**业务语义是用户-优惠券关联表**，一行 = 一次领取 | 不要用它暗示"交易"。描述它的**动词**是"领取"，不是"下单" |
| **已支付 / 支付 / 退款 / 未支付** | — | **已删除的概念**，三方支付不接 | 任何地方都不要再出现——**除了**"为什么不做"的说明里 |

**一条必须钉死的辨析：「已使用」≠「已支付」。** 券是免费领的，用户到店后线下付钱给商家，这笔钱不进系统，所以「已支付」这个态不需要；需要的只是「已使用」。连带：状态字段回来（`used`）不等于支付回来，`pay_type` / `pay_time` / `refund_time` 照删。

## 运行

**一键起依赖（MySQL 8 / Redis）**：`docker compose up -d`，容器首次启动会自动按序导入 `src/main/resources/db/` 下的
`hmdp-schema.sql`（建表）→ `hmdp-seed-data.sql`（种子数据）→ `worker_node.sql`（UidGenerator 节点表）。
注意容器内 3306 映射到宿主机 **3307**（本机 3306 通常已被 Windows MySQL 服务占用）；改了 SQL 想重跑需先 `docker compose down -v`。

JDK 8 · MySQL · Redis · RocketMQ → 起依赖 + 导入上述 SQL → 填写 `application.yaml` 占位配置 → 启动即可（领券只有一条写路径，无需选择）。  
网关示例配置（仅网关令牌桶限流，不做业务缓存）：`src/main/resources/openresty/`。

**可选观测栈**：`docker compose up -d prometheus grafana` → Prometheus :9090、Grafana :3000（admin/admin），
秒杀面板自动导入；面板说明与 PromQL 速查见 `docs/observability.md` 第 7 节。
