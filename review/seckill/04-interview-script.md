# 面试口述

## 30 秒

我实现并验证了一条限时领券链路：入口先做活动窗口和用户限流，再通过 RocketMQ 事务消息触发 Redis Lua 原子扣库存与一人一券，提交后由消费者异步把领取记录和数据库库存扣减放在同一事务里。MySQL 是最终真值，活动后用精确等式做对账。20 条 pytest 覆盖并发、窗口、限流、补偿和 Redis/MQ 故障；300 库存压力测试最终正好落 300 条领取记录，没有超卖。

## 2 分钟

这条链路最重要的不是“用了 Redis 和 MQ”，而是每层职责明确。Redis Lua 是入口资格裁决，原子完成库存预扣和用户去重；RocketMQ 事务消息解决预扣与消息提交之间的崩溃窗口；MySQL 事务把插入领取记录和 stock-1 绑定，唯一索引做最后防线。HTTP 返回 orderId 后不假装数据库已经完成，而是提供独立限流的结果查询接口。

故障语义统一 fail-closed。活动开始后 Redis 库存 key 丢失时不能拿可能落后的 DB 库存回填；MQ 发送失败也不能继续放行。消费者失败则有有界重试、死信和活动后对账。测试上我不用“成功数不超过库存”这种弱断言，而是验证 DB stock 等于初始库存减记录数，记录数等于去重用户数，再核对 Redis stock/order/claim。

我还做了真实故障和压力验证。pytest 20/20 通过；100 线程约 650 req/s、平均 141ms，500 线程吞吐没有增长而平均延迟到 759ms，说明当前单机在约 630~650 req/s 附近进入排队。这个数字只作为本机记录，不包装成生产容量。

## 常见追问

### 为什么不能只用 Redis Stream 或普通 MQ？

核心不是中间件名称，而是预扣和消息提交的原子边界。事务消息让 broker 根据本地 Lua 结果 COMMIT/ROLLBACK，并能通过 txn marker 回查；普通先扣后发存在进程崩溃窗口。

### Redis 成功为什么不直接告诉用户最终成功？

Redis 成功只代表资格预扣成功，MySQL 领取记录尚未落地。入口返回 orderId，queue 状态先写 WAITING；数据库降级时返回 ORDER_PROCESSING，让前端继续查询，不谎报最终成功。

### 如何证明一人一券？

正常路径由 Lua 用户集合拦截；消息重投由 orderId 主键幂等；数据库 `uk_user_voucher` 是最后防线。并发测试同时验证记录数、去重用户数和 Redis 用户集合。

### Redis 丢库存 key 为什么不查 DB 回填？

活动中 DB 库存可能尚未反映所有 Redis 预扣。用它回填可能凭空增加库存导致超卖，所以选择 fail-closed，活动结束后再以 DB 领取账统一重算。

### 为什么 500 线程反而慢？

吞吐已经封顶，新增线程只排队。当前有 100 并发业务舱壁、Tomcat 线程和同步 MQ 发送等上界；500/629≈795ms，与实测 759ms 接近。
