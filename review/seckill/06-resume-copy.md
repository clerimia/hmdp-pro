# 限时领券简历描述

## 推荐版本

**高并发限时领券与最终对账**：围绕校园优惠券限量领取场景，实现 OpenResty/Nginx 全局令牌桶、Java 端基于 Redis ZSet 的用户滑动窗口，以及 Resilience4j 信号量舱壁三层流量保护，分别应对全局流量洪峰、单用户高频请求和应用并发资源耗尽。领券链路使用百度 UidGenerator 生成分布式唯一领取记录 ID，并通过 RocketMQ 事务消息衔接 Redis Lua 资格裁决与异步落库：Lua 原子完成库存校验与扣减、Set 一人一券判断、Hash 用户与领取记录 ID 映射，以及事务回查标记写入；校验成功后提交事务消息，由消费者异步创建领取记录，并在同一数据库事务内执行库存条件扣减。消费端通过领取记录主键保证消息重投幂等，通过 `user_id + voucher_id` 唯一索引保证一人一券，并以 `UPDATE stock = stock - 1 WHERE stock > 0` 作为数据库侧防超卖屏障。针对 Redis、RocketMQ 和 MySQL 分别配置熔断与故障隔离，结合消息有界重试、死信监控和定时对账，实现缺失领取记录补偿及活动结束后的库存重算。AI 辅助设计 20 条 pytest，覆盖活动开始/结束时序、100 用户并发售罄、一人一券、补单、库存重算及 Redis/RocketMQ 故障；本机 JMeter 100 线程实测约 650 req/s，300 份库存最终精确生成 300 条领取记录，DB 与 Redis 四方对账一致。

## STAR 面试展开

**S（场景）**：限量券高峰存在超卖、重复领取、Redis 预扣后消息丢失、消息重投重复落库和依赖故障扩散风险。

**T（任务）**：建立入口高并发资格裁决、可靠异步落库、故障隔离和可验证的最终一致性闭环。

**A（行动）**：

- 使用 OpenResty/Nginx 全局令牌桶、Redis ZSet 用户滑动窗口和 Resilience4j 信号量舱壁构建三层流量保护；提交与结果查询使用独立配额。
- 使用 Redis Lua 原子完成库存判断与扣减、Set 用户去重、Hash 用户到领取记录 ID 的认领映射和事务 marker 写入；活动中库存 key 丢失时 fail-closed。
- 使用 RocketMQ 事务消息，根据 Lua 本地事务结果提交或回滚；消费端以独立有界线程池处理消息。
- 在数据库事务中绑定领取记录插入和 `stock = stock - 1 WHERE stock > 0` 条件更新，以领取记录主键和用户券唯一索引承担消息重投幂等、一人一券与数据库侧防超卖。
- 按 Redis/MQ/DB 拆分熔断器，结合消息有界重试、死信监控和定时对账完成补单与活动结束库存重算。
- 用 pytest 注入活动边界、并发竞争、保护档位和 Redis/MQ 故障；用 JMeter 与 DB/Redis 四方对账联合验证性能和正确性。

**R（结果）**：抢券回归 20/20 通过且禁用重跑；300 库存并发压力最终 DB stock=0、领取记录=300、去重用户=300，Redis order/claim 各 300；100 线程本机吞吐约 650 req/s。500 线程吞吐进入平台且延迟升高，据此识别当前单机容量拐点并停止无效加压。

## 口径边界

本次 JMeter 与应用运行在同一台开发机，流量直连 8081，没有经过 OpenResty；因此简历只写本机实测，不写网关 429 或生产容量。所谓无超卖限定在 20 条自动化和 300 库存压力范围内；系统是 Redis 预扣、MQ 异步落库、DB 最终对账，不是跨资源强一致事务。
