# 登录链路面试口述与追问

## 30 秒版本

我负责校园餐饮评价平台的验证码登录链路和自动化测试。发码侧使用 Redis `SET NX EX` 做 60 秒幂等冷却，重复请求不生成、不覆盖验证码；登录侧通过 Redis Lua 原子完成验证码校验、一次性消费、错码计数和五次锁定；成功后把用户摘要写入 Redis，token 采用 30 分钟滑动 TTL，并支持幂等登出。我用 pytest 从 HTTP、Redis 和 MySQL 三个观察面设计了 23 条用例，覆盖边界、安全状态、自动注册、会话续期和 Redis 故障，最终全量回归通过。

## 2 分钟版本

最初这条链路沿用教学项目实现，正常登录能跑，但验证码可以重复使用、发码和错码没有限制、token 有效期过长、logout 也没有实现。我没有直接改代码，而是先把公共接口确定为测试 seam，用 pytest 写可稳定复现的失败用例。

一次性验证码不能简单写成 GET 后 DEL，因为并发请求可能同时读到正确值。我把检查锁定、验证码比较、错误计数、触发锁定以及成功删除放到一个 Redis Lua 中原子执行。发码侧另设 60 秒冷却 Key，用 `SET NX EX` 保证并发请求只有一个生成验证码，其余请求幂等成功；错码五次锁定五分钟。登录成功后使用 32 位随机 token，把用户摘要存在 Redis Hash，TTL 为 30 分钟，每次有效请求滑动续期；登出删除 token 且保持幂等。

测试上我不 Mock 中间件。HTTP 是主断言，Redis 用于读取教学验证码、检查 TTL 和做状态注入，MySQL 验证自动注册。为了避免慢和不稳定，我把 token TTL 注入成 60 秒验证续期，用 DEL 注入会话失效，用 CLIENT PAUSE 制造 Redis 超时，并用 wait_until 等条件而不是固定 sleep。最后登录 23 条、pytest 全量 50 条均通过。

## 高频追问

### 为什么不用 JWT？

这里需要主动登出、滑动续期和服务端立即失效，Redis 会话实现更直接；多实例也能共享。JWT 适合减少服务端状态，但撤销通常还要黑名单或短 token 加 refresh token，复杂度并不会消失。

### Redis 挂了会不会绕过登录？

不会。刷新拦截器捕获 Redis 异常后不恢复用户上下文，后面的登录拦截器看到 UserHolder 为空，返回 401。它只是避免依赖异常冒泡成 500，不是放行受保护资源。

### Lua 为什么能保证原子性？

Redis 在执行脚本期间不会穿插执行其他命令。因此比较验证码和删除之间没有并发窗口，错码计数与锁定也不会丢更新。

### 为什么验证码错误也要放 Lua？

如果比较、INCR 和 SET 锁拆开，并发错码可能丢计数或越过阈值。把整个状态迁移放一起，返回值同时表达成功、普通失败和锁定。

### 发码冷却是不是限流？

不是一回事。冷却 Key 解决重复点击和网络重试，保证 60 秒内不重复生成或发送；长期防刷还需要手机号、IP、设备等长窗口限流和短信供应商配额，我不会声称当前已经实现这些。

### 为什么测试直连 Redis，不算白盒耦合吗？

业务结论仍由 HTTP 判断。直连 Redis 只服务于教学环境取码、TTL 观察和故障/状态注入，是预先约定的基础设施 seam；不会断言某个 Java 私有方法被调用。

### 为什么不用 sleep？

固定等待把机器速度当成正确性条件，容易又慢又 flaky。`wait_until` 等待真实状态，条件一成立就结束，超时还能报告最后观察值。

### 23 条测试如何选出来？

不是凑数量，而是按状态空间划分：发码输入与频控、登录输入与验证码状态、用户注册、token 生命周期、鉴权边界和 Redis 故障。每组都覆盖正常、边界和异常转换。

### 项目最大的测试开发亮点是什么？

不是“会用 pytest”，而是能从公共接口出发构造确定性状态，跨 HTTP/Redis/MySQL 验证不变量，并用失败测试推动真实缺陷修复后形成回归资产。
